Loan 01 QC Results — Explained

Why the full run shows hundreds of results when the answer key only lists 5 defects — and what it means

The short version

Nothing is broken. The engine correctly found all 4 of the 5 known defects that a rule exists for. The "hundreds of results" you see are not new problems — they are the honest, visible byproduct of running our entire rulebook against a loan file that was only ever built to contain 5 deliberate defects. The system is telling us, truthfully, "I don't yet have enough information to clear these checks" — rather than guessing.

1. What loan 01 actually is

Loan #2025-0917-001 — a Conventional/Fannie Mae purchase loan (Smith, Charlotte NC) — is a deliberately minimal, 10-document synthetic test file, built to exercise exactly 5 known QC defects. It intentionally does not contain the dozens of specialty documents a real closed loan file might have (DU Underwriting Findings, ICPL, ARB approval letters, HomeReady income-limit worksheets, gift letters, VOMs, etc.) — because it was never meant to.

Not a gap in what we compiled — the rule itself doesn't exist in either sheet of the source workbook. Either the real client checklist doesn't test this, or it lives somewhere we haven't been given. Worth a direct question back to the source.

2. Why does the full run show ~2,400 NEEDS_REVIEW and ~87 FAIL, not 5?

Because the engine isn't just checking for these 5 defects — it's running every applicable rule from the entire client rulebook (1,076 rules that could apply to a Fannie Mae purchase loan) against this one file. Two honest reasons drive almost all of the extra volume:

a) "We don't know yet" (NEEDS_REVIEW) — the large majority

Most rules ask about a fact this project hasn't been taught to look for yet in any loan file — not "this loan doesn't have it," but "we've never built a way to check for it, for any loan." The system is deliberately conservative here: rather than assume the answer is "fine, doesn't apply" (which risks quietly waving through a real problem), it flags it as needs a human to look. That's the safer failure mode, by design — but it does mean the count looks alarming until you know why.

b) Checks for documents this file was never given (FAIL)

A number of the FAIL results are unconditional "is this document present?" checks — for documents like DU Findings, ICPL, or HomeReady limits that this 10-document synthetic file simply never included. Right now the engine doesn't yet know which specific checks require which specific document, so it flags every one of them, even the ones that plainly wouldn't apply to a file this size. This is a known, already-scoped fix in progress (teaching the engine "this loan doesn't have Document X, so skip checks that need Document X" — rather than flagging every one as a failure).

3. Did we miss anything by only using the Post-Closing rulebook sheet?

We checked this specifically. This project only ever runs the Post-Closing sheet of the client's rulebook (the correct sheet for QC on an already-closed, funded loan). We confirmed, directly against the source Excel file, that:
  • Nothing from the Pre-Funding sheet is mixed in by mistake — verified in the compile logic itself.
  • The missing appraisal-mileage rule (defect 5) isn't hiding in the Pre-Funding sheet either — we searched it directly and it isn't there.
So this isn't a "wrong sheet" problem — it's either a rule that doesn't exist in the client's checklist at all, or one that hasn't been given to us yet.

Bottom line

The volume of NEEDS_REVIEW/FAIL results is not a false alarm and not a bug — it's the system honestly reporting the gap between "everything we could theoretically check" and "everything we currently know how to check," for a file that was only built to test 5 specific things. The 5 known defects themselves are resolving correctly (3 always were, 2 just got fixed) except for the 2 with genuine, already-tracked gaps described above.
