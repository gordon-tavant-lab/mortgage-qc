How a closed loan flows from Touchless into QC, and back — automatically

Touchless is the loan origination system — it produces the MISMO XML loan data and runs document extraction/classification internally. This is the integration boundary: when a loan closes, an event fires, the QC module pulls the already-extracted JSON, runs the existing deterministic engine, and posts a JSON verdict back — as a separately deployable module Touchless's own CI/CD can include or exclude behind a feature flag. This document is an architecture sketch to align on the shape, not an implementation — every box is a design decision, not yet code.

The Inclusion Mechanism

A CI/CD feature flag, living in Touchless's code — not QC's

QC is never linked into Touchless's own build artifact. The flag controls one thing only: whether Touchless's own integration code fires the outbound call after a loan closes.

qc_module_enabled = true

Touchless's post-closing workflow fires the loan-closed event to QC. Toggled per-environment or per-lender in Touchless's own config/feature-flag system — QC's release cadence is completely decoupled from Touchless's.

qc_module_enabled = false

The post-closing workflow completes exactly as it does today, with no call out at all. QC is absent from the runtime path entirely — not a no-op call, no call.

This is why QC has to stay a separate deployable rather than an embedded library (the branch we resolved earlier): a compiled-in dependency can't be excluded per-environment without a Touchless rebuild, which defeats the point of a flag. A network-called service can be toggled without touching Touchless's own build at all.

For Whoever Builds This Next

Left open on purpose — decide when this moves from diagram to spec

Transport mechanism

Webhook, message queue (SQS/EventBridge-style), or something Touchless already has for other integrations? Drawn generically above on purpose — pick whatever Touchless's existing integration patterns already use.

Retry & idempotency

If QC is down when the event fires, or the callback fails, who retries, and how does a duplicate "loan closed" event not trigger a duplicate signed run? Not addressed here.

Auth between the two services

Service-to-service auth for both the extraction-pull (step 4) and the callback (step 8) — not designed here, purely a diagram-level gap.

Where NEEDS_REVIEW actually gets worked

Explicitly deferred per this session's scope call (step 9) — does a human use Touchless's own UI, or QC's existing ExceptionReview.tsx? Both remain possible; this diagram doesn't pick.

Ruleset currency at invocation time

Step 6/7 assumes "the current signed ruleset" — if a version is mid-promotion-gate (v3 Phase 6) when a loan closes, which version actually runs? Worth a real answer before build.

Reconciling the Touchless=LOS framing

CLAUDE.md, THESIS.md, and PRD.md all currently describe Touchless and the LOS as separate. If this unified model holds, those documents likely want a note or update — flagged, not done here.
