Mortgage QA/QC engine — the complete, step-by-step system workflow

Every process, condition, decision point, gate, and human-in-the-loop (HITL) checkpoint a closed loan file passes through, from document intake to a reviewer clicking "Clear this loan and open next." This supersedes architecture-doc-v2.html: v2 was written in plain language for a non-technical reader; this edition is written for an architect — every step names its real source file, its exact pass/fail condition, and whether a human is structurally required to act. Orientation

The shape of the system, before the detail

Two hard phases, one boundary. Compile-time is where all interpretive uncertainty (LLM, human judgment) is allowed to live — it runs once per rule, is slow, and is gated by sign-off. Run-time is a pure function of (signed_ruleset, loan) → verdicts — it runs once per loan, every time, and contains no LLM, no network call, no floating-point money math, and no wall-clock.

Compile-time (Steps 3–14)

Runs once per rule (or on rulebook/Guide change). LLM drafts, deterministic screens narrow it, human sign-off is the last word. Produces one artifact: a SHA-256-hashed, signed Ruleset.

Run-time (Steps 15–19)

Runs once per loan, every time it's run. engine.run(loan, ruleset) — no LLM, no I/O, Decimal-only math, ordered by the signed ruleset's own check order. Same inputs → byte-identical output, forever.

Post-hoc & feedback (Steps 20–26)

Narrative generation, the audit hash-chain, the human Exception Review workshop, and the eval/promotion loop that gates whether a new ruleset version is even allowed to replace this one.

Where a loan physically enters this flow: only at the boundary between compile-time and run-time — after the Guide reference, the fact vocabulary, and the ruleset are all already signed. Nothing loan-specific ever touches the compile-time LLM calls; they never see a real loan's data.

The Workflow

Step-by-step, source-file-cited

26 steps across 6 phases. Every GATE step states its exact pass/fail condition. Every HITL step states who acts and what their options are. Nothing here is aspirational — each step cites the real module that implements it, or is explicitly marked 015 · DRAFT, NOT BUILT where the behavior described is approved-but-pending.

PHASE 1Compile-Time: Rule Interpretation (runs once per rule)

The only place an LLM is allowed to be uncertain. Every step here is screened by a deterministic gate before its output can reach a human for sign-off.

10
Domain-knowledge grounding + investor-mismatch gate + judge-panel escalationGATEHITLLLM

Each signed fact is searched against the real, ingested Fannie Mae Selling Guide (416 sections) and given a page/section citation — never rewriting Guide text, only pointing at it. PHASE 2Sign-Off & The Signed Artifact

The hard boundary. Nothing past this point is allowed to run against anything unsigned.

13
SME sign-off gate — the one that isn't theater by constructionGATEHITL

RuleProvenance computes Levenshtein edit-distance between what the LLM drafted (llm_draft) and what the SME actually signed (signed_text). Ruleset.signoff_summary() reports rules_total / rules_edited_by_sme / mean_edit_distance; unedited_rules() lists every rule signed with zero change. A ruleset where every edit distance is 0 is a visible red flag — evidence of rubber-stamping, not review. This is a direct internal-review correction: "compile once, SME signs off" only means something if you can measure that signing actually happened.

p0/qc_engine/ruleset.py:RuleProvenance, signoff_summary()
14
The signed ruleset artifact — content-addressed by SHA-256DET

Ruleset.sha256() hashes the canonical, sorted JSON of {ruleset_id, version, engine_version, checks} — not the LLM draft text or provenance (audit context, not executable content). The runtime loads a ruleset by hash: given the hash, the exact rules that judged any loan are forever recoverable, and two rulesets sharing a hash are provably identical rule-for-rule.

p0/qc_engine/ruleset.py:Ruleset.sha256(), canonical_content()
PHASE 3Run-Time: Per-Loan Evaluation (runs every time, zero LLM)

engine.run(loan, ruleset) — deliberately boring: [_eval_check(loan, c) for c in ruleset.checks]. Nothing here calls out, retries, or branches on anything but the data already in front of it.

15
Applies-if precondition gate (per check, pre-dispatch)GATE

Every condition in chk.applies_if is evaluated (AND-combined) before kind dispatch. A confirmed non-match on any condition short-circuits to NOT_APPLICABLE immediately — even if another condition's field is unknown (a definite non-match outranks an unknown one). If no condition definitely fails but one has an unknown field, resolves NEEDS_REVIEW / APPLICABILITY_UNKNOWN instead of guessing either way.

p0/qc_engine/engine.py:_eval_applies_if() lines 124–158
16
Kind dispatch — 6 deterministic check archetypesDET

Every check is exactly one of 6 kinds, each a closed-form comparison:

agree_categorical[RECONCILE] DOC vs SYSTEM under a normalizer. Mismatch → informational FLAG, not a QC failure (docs are truth; QC runs on them regardless).
agree_numeric[RECONCILE] DOC vs SYSTEM within a tolerance. Same FLAG-not-FAIL semantics.
predicate[QC] is_true / is_present — a missing value is a real FAIL, not exempted.
ratio_threshold[QC] LTV / DTI / a raw field floor-ceiling vs an authored threshold — the bit-exact money moment.
agree_doc_categorical[QC] Two independently-extracted document fields (never a system source either side). Mismatch → real FAIL — a genuine closing-package defect, not a sync lag.
agree_doc_numeric[QC] Numeric counterpart to the above, within tolerance.
p0/qc_engine/engine.py:_eval_check() lines 161–396
17
UNSPECIFIED-threshold honesty guardGATEHITL

If the compiler honestly declined to invent a tolerance/threshold the source AMQ row never stated, the check carries the literal value "UNSPECIFIED". The engine treats this as neither "no data" (NOT_APPLICABLE would hide it) nor a crash — it resolves NEEDS_REVIEW / UNSPECIFIED_THRESHOLD, explicit and human-facing: "a confident invented number is worse than an honest gap" (the rule-fidelity hardening of 2026-07-22).

p0/qc_engine/engine.py lines 207–218, 288–293, 339–349
18
Confidence gate — the one place auto-clear is withheld on a technical PASSGATE

A PASS that relied on a low-confidence document extraction is downgraded to NEEDS_REVIEW (LOW_CONFIDENCE) — not auto-cleared. Default floor: 0.80. This is deliberate: a confident-but-wrong OCR read is the dominant residual risk once the engine itself is provably correct, so the system routes around it rather than trusting extraction accuracy blindly.

Open tension (RED, per ROADMAP)0.80 is a mechanism, not yet a calibrated number — Touchless confidence hasn't been characterized on real docs. "Deterministic given the extracted inputs," honestly, until then.
p0/qc_engine/engine.py:DEFAULT_CONFIDENCE_FLOOR = 0.80, lines 408–418
19
review_reason tagging — one generic rule, open vocabularyDET

Tagged generically by phase + status, not per check-kind — so a future kind is auto-tagged with zero changes here. A QC-phase FAIL/WARNING → EXCEPTION. A RECONCILE-phase NEEDS_REVIEW → SOURCE_INCOMPLETE. A FLAG never gets a reason (it isn't a review-worthy exception by design).

PHASE 4Disposition & Explanation (per loan, post-run)
20
Disposition composition — the one per-loan verdictGATE

Composes every check's verdict into one status: AUTO_CLEARED or NEEDS_REVIEW — provably equivalent-by-construction to "no qc_failures and no needs_review" (spec FR-006). review_reasons is the deduplicated, open, multi-label set of every contributing reason across all checks; a loan can carry more than one concern simultaneously, none privileged over another.

p0/qc_engine/engine.py:RunResult.disposition, review_reasons lines 476–491 · 004-loan-disposition
21
Decision narrative — the one place an LLM touches a real resultLLMGATE

A per-loan prose summary of an already-computed RunResult, grounded in that result plus the signed fact vocabulary's Guide citations. Four guardrails keep this from reopening determinism: (1) generated exactly once per RunResult, never regenerated live; (2) validated closed-set — every check_id / citation / review-reason it references must already exist in the real result, or the generation fails validation and bounded-retries; (3) read-only, never parsed back into routing/gating (enforced at the source level — engine.py's own text never names this artifact's key); (4) wording may vary on regeneration, the facts asserted may not. New, disclosed cost: this is the one genuine per-loan-per-run LLM call in the pipeline — tracked honestly, never folded into the otherwise-real "$0" claim.

p0/qc_engine/compiler/decision_narrative.py (434 lines) · 014-decision-narrative
22
Immutable, hash-chained audit logDET

Every run is appended as a record hashing {prior record's hash + this run's canonical content} — loan id, ruleset hash+version, engine version, and the full per-check field intermediates. Tampering with any historical record breaks every subsequent hash. verify_chain() recomputes every link on demand. S3 Object Lock gives WORM (can't delete) but not verifiability-of-history; this hash chain is what actually proves the sequence was never altered.

PHASE 6Continuous Eval — Gating the Next Ruleset Version

This phase never touches a live loan. It decides whether a changed ruleset is even allowed to become the one Phase 3 runs against.

25
Promotion gate — hard block on any false-auto-clearGATEHITL

Before a new/changed ruleset version is ever allowed to run for real, it must pass 3 test tiers plus label-free invariants — a single enforceable promotion_decision (PROMOTE | BLOCK) with a real, non-zero exit code on failure.

GOLDENDid a known-correct case regress?
COVERAGEDoes every compiled check have a proven pass/fail scenario at all?
VOLUMEAt realistic population scale, what fraction auto-clears, and does zero-false-auto-clear still hold?
Metamorphic invariantsMonotonicity, reconcile soundness, engine self-consistency, confidence gate — label-free, run against the actual candidate

The hard block: a false-auto-clear from any tier sets BLOCK, naming the offending check/loan/expected-vs-actual — never aggregated away into a bare count. Any known-good result that flips must be acknowledged by a human on purpose before the new version can ship.

Core data model

SourceValue

truth (DOC side, always closing-file) + sources (open, named map — today los/mismo, N-source-ready without a code change) + citation (DocCitation) + doc_confidence. system_value() resolves through source_priority. doc/los/mismo remain as backward-compatible read-write properties.

CanonicalLoan

loan_id, loan_type, a canonical field_name → SourceValue map, and pre-derived numeric facts (e.g. monthly income/debts) for ratio checks. The engine never parses a raw source — adapters populate this once.

Check / Ruleset

A Check is one deterministic assertion: kind, phase (RECONCILE|QC), field_name, applies_if, plus kind-specific fields (tolerance, threshold, ratio, operator, predicate, compare_field_name). A Ruleset is a list of Checks + RuleProvenance + RuleIntentRecord, hashed by sha256().

CheckResult / RunResult

Per-check: status (PASS|FAIL|WARNING|NEEDS_REVIEW|NOT_APPLICABLE|FLAG), inputs, normalized, compared_value, rounding, citation, review_reason. Per-loan (RunResult): composes into disposition, review_reasons, qc_failures, flags (informational, non-blocking), needs_review.

A real citation, exactly as it appears in the audit trail — pointing at a source that already exists, never inventing one:

fact: gift_funds_used
cited to:
  - Fannie Mae Selling Guide B3-4.3-04, Personal Gifts (02/04/2026)
  - Fannie Mae Selling Guide B3-4.2-02, Depository Accounts (12/14/2022)
applies_if: gift_funds_used == "true"
# if gift_funds_used resolves False on this loan, the check short-circuits to NOT_APPLICABLE at Step 15 — it never even reaches kind-dispatch.

The determinism proof, mechanically

Two properties make "same loan → same verdict, forever" provable rather than asserted:

No float touches a money/ratio decision

money.py converts everything to Decimal via string representation (never through a float literal), pins ROUND_HALF_EVEN explicitly, and quantizes to a fixed scale per value class — cents (0.01), rate-percent (0.001), ratio (0.0001), percent (0.001). LTV/DTI boundary checks are exactly where float drift would silently flip a pass/fail.

Reconciliation logic is signed data, not code

reconcile.py's NORMALIZERS map (norm_name, norm_address, norm_ssn_last4, norm_zone, norm_identity) is a fixed, version-pinned interpreter of named transforms the signed ruleset references by name — not hand-coded per-field judgment living outside the audit trail.

The G3 bake-off finding, precisely: at temp=0, both Haiku 4.5 and Sonnet 4.6 were byte-identical across 5 runs × 6 loans — "the LLM varies" is false at this scale, for either model. What actually decided compile-then-run: Haiku reproducibly cleared a 98.0% LTV loan against a 95% program max (a buyback-grade error, the same wrong answer every time); Sonnet caught it. Accuracy was model-dependent and unknowable in advance — disqualifying on its own, regardless of determinism or the (much smaller than assumed, ~$27–$70/10k-run on synthetic payloads) cost delta. For the architect specifically

Open decisions this workflow does not silently resolve

Per the project's own "surface, don't silently diverge" discipline — these are the load-bearing risks/decisions an architect inheriting this system should know are still open, not settled.

Confidence floor is a mechanism, not yet calibrated (RED)

The 0.80 floor at Step 18 cannot catch confidently-wrong extractions until Touchless confidence is characterized on real documents. Gate G2.

The false-auto-clear ≈ 0 claim is synthetic until 012 completes (RED)

The eval is correct by construction; the population false-clear rate waits on Kayla's expert-labeled real loans (Gate G1). Until then, it's the regression floor, not the real-world number.

Trust-ordering vs. demo-ordering (AMBER)

The engine is sequenced to earn trust before the Author surface (self-service routes→blocks→checks authoring) is real — but the authoring magic is what won the room with the client. Deliberate choice; the example/ prototype carries the demo experience in the interim.

NL-authoring vs. sign-off-theater hole (AMBER→RED on the criteria layer)

Type-it-in-English rule authoring is the feature most likely to delight — and targets exactly the field (the applies_if criteria gate) where a wrong-but-plausible artifact most easily survives SME sign-off, because the SME can't fluently read what they're signing. Recommendation on record: NL never emits the gate as free text; it only proposes into a catalog-constrained control the SME confirms value-by-value.
