Documentation · How This Is Built, and Why

Deterministic QA/QC for closed mortgage loans

This engine turns a 7,211-row client rule workbook (Retail) and a 416-section Fannie Mae Selling Guide into a signed, cited rulebook — then runs it against real closing packages using plain code, with no AI involved in actually deciding a loan's result. Everything below explains why it's built this way, as one continuous system rather than a pile of separate features.

The Thesis

Three layers, one principle

Compile-time cognition, runtime determinism, human sign-off before either is trusted. Nothing in the decision path is allowed to be non-reproducible.

01COMPILE-TIME · LLM

Ground the rules once

An LLM reads the raw rulebook and the real Selling Guide at compile time only — decoding questions, canonicalizing facts, attaching Guide citations, drafting preconditions. It never sees a loan at evaluation time.

02RUNTIME · ENGINE

Decide deterministically

The compiled ruleset runs against a loan through the same plain-code engine every time. Feed it the same loan and the same ruleset twice, and it gives the exact same answer both times — because no AI model is involved in making the actual decision, only fixed code following fixed rules.

03HUMAN · SIGN-OFF

Nothing ships unsigned

Both the Guide reference and the fact vocabulary sit behind an explicit sign-off — if anyone ever tries to run a loan against one that hasn't actually been reviewed and approved by a person, the system refuses outright rather than quietly using it anyway.

The AI never decides a verdict on a loan. It only helps build and ground the rules, ahead of time, before any loan is ever checked. Once those rules are built, plain code — not AI — is what actually evaluates each loan. And a person signs off on that rulebook before it's trusted for real use. That three-way split is the whole design — and the direct answer to "if a regulator asks how you calculated that number, can you explain it, or do you have to buy the loan back?"
Scope

What this project builds vs. what it reuses

Reading a loan's documents and pulling data out of a lender's own systems are both already-solved problems, handled by separate, existing tools — this project deliberately doesn't rebuild either one. It puts all its effort into the one thing nobody has solved yet: turning the client's rulebook into rules a computer can actually trust, and running them correctly against real loans.

THIS PROJECT

The rules engine, start to finish

Decoding the rulebook, deciding which rules apply to which loan, running the checks, explaining the result to a reviewer in plain language, and keeping a full record of how every decision was reached — one continuous piece of work, not separate hand-offs between teams.

REUSED, NOT REBUILT

Reading documents & the lender's system

Pulling the actual values out of a loan's documents — and figuring out which document is which — is handled by Touchless, a separate, already-existing system. Getting data out of the lender's own loan system uses an existing connector. Both are treated as ready-made inputs to this project, not something it builds itself.

The Ontology Approach

Turning a messy spreadsheet into rules a computer can trust

The client hands over a 7,211-row Retail spreadsheet used today to audit closed loans by hand. It's a checklist written by people, for people — not a database. The exact same real-world question ("is there an appraisal in this loan's file?") shows up under four different row numbers, worded slightly differently each time, with nothing anywhere saying they mean the same thing. Compile that literally and you'd get four separate rules that could each independently decide "yes" or "no" about the same loan — and disagree with each other. The four steps below turn that into one shared, trustworthy set of facts, with a person signing off on every name. (The "Architecture" section right after this one shows exactly where these steps sit in the bigger picture.)

NO AI — PLAIN CODE

Step 1 — Find the real questions

A simple, rule-based program (no AI involved) reads all 7,211 rows and groups the ones that offer the exact same list of answer choices — a strong sign they're really the same question. This found 24 real, distinct questions hiding inside 3,275 of the rows, and copies every answer choice exactly as written — it never rewrites or guesses at wording.

A PERSON APPROVES

Step 2 — Give each fact one name

Someone has to decide what to actually call each of those 24 questions (e.g. "did this loan use gift funds?") — the one step that takes real judgment, so a person reviews and signs off before it's used. This step caught something useful: 4 of the 24 "questions" turned out to be the exact same real fact asked four different ways — now merged into one, so two rules can never quietly disagree about it. 16 facts approved so far.

POINTS TO THE REAL GUIDE

Step 3 — Show your source

For each of those 16 facts, the system searches the real, official Fannie Mae guidance manual (416 sections, real text) and attaches a page reference to wherever that fact is actually defined — e.g. "gift funds" points straight to the Guide's real Personal Gifts section. It only ever attaches a pointer, never rewrites or invents guideline wording, so anyone can go check the source themselves.

AUTOMATIC, ONLY WHEN CERTAIN

Step 4 — Only apply a rule when it fits

A rule written for gift-funded loans shouldn't run on every loan — it should skip the ones with no gift. This step decides, automatically, which loans a rule applies to. But only when it's completely sure; anything even slightly ambiguous is set aside for a person to check rather than guessed at.

The Gates

Every point where the system is allowed to refuse

A gate's job is to convert "we're not sure" into an honest, distinct signal — never a silent guess, never a default answer. Every gate below is real, live in this codebase today, not aspirational.

Sign-off gate

The Guide reference and the fact vocabulary are unusable for resolution until a person has actually reviewed and approved them.

On failure: the system refuses outright — it will not silently fall back to an unreviewed version.

Operator consistency gate

Detects known-inverted check families (a comparison compiled backwards — e.g. "greater than" flipped to "less than") before a ruleset ships.

On failure: the check is excluded from the signed set and listed, not silently shipped inverted.

Program applicability gate

A rule only fires for the loan program it was actually written for (Conventional/FHA/VA/USDA) — honoring the workbook's own encoded gating rather than running every rule on every loan.

Conditional applicability gate

Decided before a check ever runs. A confirmed non-match on the condition means the check is skipped, correctly, as not applicable. An unknown value on this loan (no data yet) means the check is set aside for review, tagged as an applicability question — never silently skipped, never silently run.

Investor-mismatch gate

If a fact's own description names an investor or agency the loaded reference corpus isn't for (e.g. a Freddie Mac fact against a Fannie-only corpus), citations are refused outright — regardless of how well it otherwise matched. Caught by an adversarial review this session on a real shipped artifact, fixed same-day.

Confidence gate

A low-confidence extracted value withholds auto-clear even on a technical pass — an extraction-trust problem, not a defect, and tagged as its own distinct concern rather than conflated with a genuine QC exception.

Disposition gate

Composes every check's verdict into one clear status — cleared, or needs review — with an open set of specific reasons attached (a real exception, incomplete source data, low confidence, an applicability question). A loan can carry more than one of these at once, and each is called out individually rather than collapsed into one flat "something's wrong."

Explaining The Result

A narrative a person can actually read, and a record that backs it up

Once a loan gets its verdict, two more things happen — both read-only, neither able to change the outcome.

Decision narrative

The one place an LLM is allowed to write prose about a result, not a rule — a per-loan summary explaining why it got its disposition. It's grounded in two real sources, never one alone: the loan's own findings (which checks fired, what they cited, why it needs review) and the real Fannie Mae Guide section behind each one, pulled from the same signed facts the rules were compiled from — so a reviewer learns not just that a check failed, but which real Guide requirement it traces to. Guardrails keep this from reopening determinism: generated once and cached, never regenerated live; every claim and every cited Guide section checked against the loan's real result and the signed facts, with an honest "no Guide section attached yet" when one genuinely isn't there, never an invented one; read-only, never parsed back into routing or gating; and the wording may vary on regeneration, but the facts and citations it states may not.

Audit trail

Every stage of a real run is logged in detail — derivation evidence, precondition decisions, every check's input, method, verdict and citation, comparisons against prior versions, and an explicit cost summary. A real 5-loan run produced 24,050 such log entries; $0.00, 0 LLM calls, reported explicitly, not just implied by omission.

5 for 5 — every result here was the right call, not just 4 of them. Four defects were caught outright, each with a real, page-cited quote a reviewer can go verify themselves. The fifth is the more important proof, not the weaker one: rather than silently treating a missing piece of extraction as "no problem," the system said, plainly, that it didn't have enough information to compare — and held the loan for a person instead of guessing. A system that guessed wrong here wouldn't just be a minor miss — it's exactly the failure mode that costs a buyback: a real undisclosed liability, cleared because nobody caught that half the comparison had silently gone missing. Taken together, this loan lands on needs review, tagged both as having a real exception and as having incomplete source data — a reviewer sees both reasons, and nothing here was ever quietly assumed clean.
